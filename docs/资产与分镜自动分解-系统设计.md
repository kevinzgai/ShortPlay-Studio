## 1. 参考文档解构（306 行 → 7 个可计算单元）

| # | 章节 | 内容 | 系统化归类 | 可否自动 |

| 2 | 二、一致性锚点 | 「3 个怪特征 + 1 个服装记忆点」→ 固定关键词串 | **结构化数据**（全篇最高工程价值） | ✅ |

| 5 | 五、场景概念图 | 5 段式模板：场景 / 陈设 / 物理光影 / 材质细节 / 镜头 | **模板渲染** | ✅ |
| 6 | 六、参数与工作流 | 全局风格锚、比例、负面词、推荐生成顺序、一致性提醒 | **项目级 StyleBible + 可计算校验** | ✅ |
| 7 | 七、下一步 | 8 段切点 / 约 2 分钟 → 15 秒段落式分镜（机位/站位/角度/光照） | **与现有 plan/storyboard 对接** | ✅ 已有能力 |

**三条最值钱的行业经验（必须编码进系统，不能只当说明文字）**：

1. **不要每个镜头重写全脸** —— 靠「3 个怪特征 + 1 个服装记忆点」做一致性，成本远低于全量重绘。
2. **固定关键词串原样粘贴，禁止重写** —— 这是可计算的校验规则（同一 asset 的 `keyword` 在所有镜头 prompt 中必须逐字出现）。
3. **同类型角色必须靠「脸型 + 瑕疵 + 服装」三者差异化** —— 文档第 287 行特意点名本章 4 个男性角色，可转成锚点唯一性校验。

**一个规则永远做不到、必须靠 AI 的点**：C02 鬼媳妇标注「不可见（设定）」，却仍列为 P0 必建资产。规则抽取只能看见出场实体；「因设定需要而预建资产」需要读全文做语义判断。

| `engine.js:755-805` | 角色 / 场景资产对象结构，含 `aliases` `weight` `refImage` `locked` `starred` `sceneNos` `source` |

| `server.py:114` `SYSTEM_SHOTS` | 9 项分镜描述卡 + `refs` 剧本行覆盖校验 |

### 2.2 生产端的真实缺口

`buildAssets()` 的信息来源只有三处：

- 角色名 ← `parsed.characters`（台词 speaker）+ 保守的「人名 + 动作动词」正则兜底；
- 外观 ← 剧本里 `林晚（27岁，便利店店员）` 这种**括号注释**（`appearanceHint`）；
- 场景 ← `[intExt, location, time]` 三元组去重。

对《鬼婚，逃命》这类小说体原文：没有括号注释、场次多为「未注明」、人物以第一人称叙述，于是
`appearance / wardrobe / persona / aliases` 全部为空、`props` 恒为空数组、场景名退化为「未注明」。
**资产对象存在，但内容是空壳** → `assemblePrompt()` 注入不进东西 → `refsFor()` 没有 `refImage` → `h3Item()` 只能判 `t2v`。

### 2.3 链路现状

```
剧本 → adapt(小说转场次) → parse(场次/行索引) → plan(分集) → storyboard(逐集分镜 + 9项卡)
     → verify(台词/动作覆盖) → export(CSV/MD/TXT/JSON + video-prompts)
                    ↑
              buildAssets()  ← 规则抽取，插在 parse 之后，但产出为空壳
```

## 3. 三个必须先定规矩的设计冲突

### 冲突 1：保真 vs 补全（最核心）

现有 `SYSTEM_ADAPT` / `SYSTEM_SHOTS` 都写死「**严禁新增剧本里没有的人物、地点、事件、道具**」。
但资产设定天然需要补全：`C02 鬼媳妇`的凤冠点翠、`C01` 的右眉尾 0.5cm 疤、`S01` 的钟馗像与转盘电话，原文一句都没有。

**解法：双通道 + 溯源标记，互不污染。**

- 剧情链（adapt / plan / storyboard）：继续严格保真，台词逐字、事件不增，一字不改。
- 资产链（assets）：允许 `inferred`，但每个字段带 `source: script | inferred | user` 与 `evidence`（原文句子编号）。
- 硬约束：**资产链的推断结果绝不回写剧本、绝不进入 `dialogue`、绝不参与剧情保真校验**。
- 用户手改字段优先级最高：沿用现有 `touched` / `locked` 语义，AI 分解时 `locked` 资产整条不动、`touched` 字段不覆盖。
- UI 用不同底色标「AI 推断」，让人审，而不是静默采信。

### 冲突 2：`refs` 同名不同义

- `SYSTEM_SHOTS` 的 `refs` = **剧本行编号**（`A1-1` / `D1-1`），用于台词/动作覆盖校验；
- `refsFor()` 的 refs = **参考图槽位**（`character1` / `character2`），用于出片入参。

**必须改名分离**：`scriptRefs`（覆盖校验）与 `refSlots`（参考图），禁止任何字段复用 `refs`。这是最容易在后期串味的一处。

### 冲突 3：单参考图硬约束

`H3_CONTRACT.multiRefSupported = false`，`i2v` 只吃一张首帧图。
所以文档第四节「线稿 + 色彩参考图双图输入」**在当前 H3 接口上跑不通**，不能硬接。分档处理见 §8。

## 5. 工作流与角色注册表

### 5.1 目标链路（新增 2 个 stage，插在 parse 之后）

```
剧本 → adapt → parse ─┬→ assets(资产大师) → assetPrompts(美术设定) ─┐
                      │                                              ├→ plan → storyboard → verify → export
                      └→ (失败时降级到 buildAssets() 规则结果) ────────┘
```

- `assets`：剧本全文 + 场次索引 → **结构 JSON**（资产清单 / 锚点 / 别名 / 优先级 / 溯源），服务端渲染成完整资产对象。
- `assetPrompts`：资产 → **结构 JSON**（三视图/概念图各段关键词），服务端用模板渲染成长提示词文本。

### 5.2 铁律：模型只出结构，正文由代码渲染

这是上一轮 `adapt` 踩过的坑：让模型重写 3000 字全文 → 90s → `max_tokens=16384` 截断 → 502。
改成「模型只输出结构 JSON + 服务端逐句重组」后，约 17.1s 完成、90/99 句保真、0 warning。

**资产分解必须沿用同一套路**：三视图提示词动辄 300–500 字 × 16 个资产，让模型全文输出必然截断。
模型只填 8 个槽位的关键词，模板负责拼装「画幅 / 体型 / 面部 / 发型 / 服装 / 配饰 / 质感光影 / 表情」与全局风格锚、负面词。
附带好处：模板一改，16 个资产全部同步换风格，不用重跑模型。

### 5.3 角色注册表 = 用户要的「skill 方式」（接入决策 2026-11-11 已更新）

```python
ROLES = [
  {"id":"adapt",        "system":SYSTEM_ADAPT,   "input":"sentences", "render":"build_adapted_script", "check":"check_adaptation"},
  {"id":"parse",        "system":SYSTEM_PARSE,   "input":"script",    "render":"normalize_scenes",    "check":"check_scenes"},
  {"id":"assets",       "system":SYSTEM_ASSETS,  "input":"scenes",    "render":"build_asset_pack",    "check":"check_assets"},
  {"id":"assetPrompts", "system":SYSTEM_ART,     "input":"assets",    "render":"render_asset_prompts","check":"check_prompts"},
  {"id":"plan",         "system":SYSTEM_PLAN,    "input":"scenes",    "render":"normalize_plan",      "check":"check_plan"},
  {"id":"storyboard",   "system":SYSTEM_SHOTS,   "input":"scriptIdx", "render":"normalize_shots",     "check":"check_coverage"},
]
```

每个角色 = `prompt + input 契约 + output schema + 渲染器 + 校验器`，注册即插拔。
后续「剧本评估 / 剧本创作 / 分镜大师 / 导演」= 往表里加一行，不动拓扑。

## 6. API 契约

| 端点 | 入参 | 出参 |
|---|---|---|
| `POST /api/ai/assets` | `{script, scenes, prevAssets, styleBible}` | `{assets, coverage, warnings, model}` |
| `POST /api/ai/asset-prompts` | `{assets, styleBible, kinds}` | `{prompts[], negative, order, aspect, warnings, model}` |
| `GET /api/config` | — | `features` 追加 `assets`、`assetPrompts` |

前端 `ai.js` 增加 `AI.assets()` / `AI.assetPrompts()`；`AI.run()` 在 `parse` 之后插入两阶段，
**任一阶段失败都降级到 `E.buildAssets()` 的规则结果**（沿用现有逐集降级思路，保证一定有资产可用）。

`SYSTEM_ASSETS` 输出契约（只出结构）：

```json
{
  "style": {"anchor":"...", "negative":"..."},
  "characters": [
    {"name":"水雷","aliases":["润土"],"code":"C01","priority":"P0",
     "visibility":"全程","age":"18岁","role":"主角",
     "anchors":{"face":"...","flaw":"...","wardrobeHook":"..."},
     "keyword":"...","source":"inferred","evidence":["S2-A3"],"sceneNos":[1,2]}
  ],
  "scenes": [
    {"code":"S04","name":"鬼婚喜宴长街","priority":"P0","intExt":"外景","time":"夜",
     "anchors":{"props":["大红灯笼","长条木桌"],"light":"暖红顶光","lens":"35mm"},
     "source":"script","evidence":["S6-A1"],"sceneNos":[6]}
  ],
  "props": [{"code":"P01","name":"黄纸铜钱","boundTo":["S02","S05"],"source":"script"}]
}
```

硬性规则与 `SYSTEM_ADAPT` 同构：`evidence` 只能引用剧本行索引里真实存在的编号；`source=script` 的字段必须能在原文找到依据；推断字段必须标 `inferred`；禁止输出长描述文本。

## 7. 校验规则：把文档里的「人工提醒」变成可计算检查

| 规则 | 来源 | 实现 |
|---|---|---|
| 角色覆盖率 | 资产清单 | `parsed.characters` 每个都必须有资产；动作正则推断出的人名也要有 |
| 场景覆盖率 | 资产清单 | 每个 `scene.no` 必须能映射到某个 `scene.sceneNos` |
| 别名归并 | `水雷/润土`、`小强/强子` | 同一实体的多个称呼合并到 `aliases`，禁止生成两张脸 |
| 锚点唯一性 | 第 287 行「4 个男性角色务必差异化」 | 同 `age` 段 + 同性别的资产，`anchors` 三元组不得全等；冲突即 warning |
| 关键词串一致性 | 第 288 行「原样粘回去，不要重写」 | 资产 `keyword` 在引用它的每个镜头 prompt 中必须逐字出现 |
| 溯源完整性 | 冲突 1 | `source=inferred` 且 `evidence` 为空 → warning，交人工审 |
| 优先级合理性 | P0/P1 | P0 应覆盖戏份 `weight>=4` 或核心场景；可提示不强制 |
| 提示词长度 | `H3_CONTRACT` | 单条 prompt ≤ 4000 字符，超出即精简并告警 |

## 8. 出片契约分档（解决「双图输入」跑不通）

| 档 | 做法 | 当前可用 | 说明 |
