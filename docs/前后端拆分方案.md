# 前后端拆分方案（2026-11-10 定稿）

> 本文是 2026-11-10 与 AI 逐条质询后定下的方案，**九条决策已全部拍板，没有「看情况」的项**。
> 目标：把前端拆成独立仓库、把 4418 行的 `server.py` 治理成可维护的包，**不改技术栈、不动 API 契约、不砸 25 套回归脚本**。
> 前置事实：路线 S0~S7 已收官，`dev` 与 `origin/dev` 同步在 `2d41d7c`，全量回归 25/25 套（5m15s）。

---

## 1. 现状诊断（先说清楚「拆」到底拆什么）

| 层 | 现状 | 判断 |
|---|---|---|
| 前端 | `frontend/` 已是独立目录，Vue 3 + Vite，**运行依赖只有 `vue`**，无 router / 无 Pinia / 无 TS | 目录上早就拆了，缺的是**仓库与构建**层面的独立 |
| 前端构建 | 产物落到仓库根 `dist/`，由 `server.py` 当静态文件托管，同源单端口 8177 | 同源是资产，别为了「看起来分离」把它拆掉 |
| 后端 | `server.py` **4418 行单文件**，43 个 `/api/*` 端点全塞在 `do_GET` / `do_POST` 的 if-elif 长链 | 这是真正「吓人」的地方 |
| 后端依赖 | Python 3.13.12，三方依赖**只有 `pillow`**，其余全标准库 | 零安装一键启动是现有优势，改造时不能丢 |
| 数据 | `projects/` 下 32MB JSON + 参考图，无数据库 | 已有 `tmp`+`os.replace` 原子写、`PROJECT_LOCK`、`schema: 2` |
| 前端体量 | `stores/studio.js` **2881 行**、`lib/engine.js` **2102 行** | 跟后端是同一个病，拆仓时顺手治 |
| 回归资产 | `tools/verify_*` 25 套 Playwright，全部打 `127.0.0.1:8177`、走相对路径 | **这是安全网**：只要 HTTP 契约不变，它们就能证明每次改动没坏 |

结论：「拆分前后端」在技术上其实是三件事——**拆仓（结构）、拆后端单文件（体量）、拆前端 store（体量）**。换框架是可选项，不是前提。

## 2. 九条决策

| # | 决策点 | 结论 | 核心理由 |
|---|---|---|---|
| 1 | 部署形态 | **本机单机自用** | 单人使用写不出并发冲突；不需要账号体系、多租户、限流 |
| 2 | 拆分边界 | **拆仓库 + 拆构建，部署仍同源单端口 8177** | 前端挪到别的 origin 会引入 CORS、预检、`baseURL` 改造，为「看起来分离」支付掉整个回归安全网 |
| 3 | 后端路线 | **两步走**：先拆 `app/` 包（零行为变更）→ 再换 FastAPI + uvicorn | 一步做完，出红灯分不清是「搬错了」还是「框架语义不同」 |
| 4 | 前端技术栈 | **Vue 3 + Vite 一个字不动**，不加 router / Pinia / TS，只拆 store | 四步工作区是 `S.step` 状态不是 URL；单 store 用不上 Pinia；5000 行 JS 迁 TS 成本远大于收益 |
| 5 | 数据层 | **保持 JSON 文件，不上数据库** | 已有原子写 + 线程锁 + schema 版本；单人单机下 SQLite 只增加迁移成本 |
| 6 | 长任务与实时 | **保留线程 + SSE，不引队列**；`uvicorn --workers 1` 是硬约束 | 出图任务表与 `PROJECT_LOCK` 都在进程内存，多进程会直接失效 |
| 7 | 密钥与配置 | **保持明文文件**（已 gitignore + `_mask_key` 脱敏），不加密钥服务 | 单机自用的真实风险只有「误提交」，这条已经堵住 |
| 8 | 拆仓方式 | **不碰历史**：新仓用当前快照 + 一条初始提交起步 | `filter-repo` 会重写全部 hash，刚推的 14 个提交全作废，收益与风险不成比例 |
| 9 | 实施顺序 | 后端拆包 → 拆仓 + 前端拆 store → 换 FastAPI | 由低风险到高风险，每步独立验收，出问题能定位到具体哪一层 |

### 明确不做

- 不做鉴权 / 登录 / 多租户（决策 1 的直接推论）
- 不上 Docker / K8s（会让 `start.bat` 双击即用变复杂）
- 不上 PostgreSQL / Redis / Celery（单机自用用不到）
- 不换 React、不用 TS 重写、不引 vue-router / Pinia
- 不改 API 路径、响应结构、状态字段名（25 套脚本的契约）

### `dist/` 归属（跨仓唯一耦合点）

**不要用 `--outDir ../另一个仓/dist` 这种跨仓相对路径**，早晚会断。做法：

- 前端仓 `npm run build` 输出到自己的 `dist/`；
- 后端读 **`WEB_ROOT` 环境变量**，默认 `./dist`（向后兼容 `python3 server.py` 双击即用）；
- 部署/CI 里把 `WEB_ROOT` 指向前端仓的 `dist/` 即可。

## 6. 最容易翻车的一处：SSE 阻塞

**这是全案比 43 个端点重写更危险的地方**，因为它的症状是「能用，但偶发全站卡住」，传统断言抓不到。

- 现状：`/api/parse/events` 走同步阻塞轮询，`parse_task_wait()` 内部 `time.sleep`。
- 风险：搬进 FastAPI 的 `StreamingResponse` 后，若在 **async 生成器**里直接调 `parse_task_wait()`，会阻塞整个事件循环 → 所有请求一起卡。
- 正确做法（二选一）：
  1. 把阻塞等待丢进线程池：`await anyio.to_thread.run_sync(parse_task_wait, task, since, 2.0)`；
  2. 改成 `await asyncio.sleep(0.2)` 轮询 `parse_task_snapshot()`，全程不碰阻塞 IO。
- 必须补一条断言：SSE 保持连接期间，并发请求 `/api/config` 的响应时间 < 500ms。
